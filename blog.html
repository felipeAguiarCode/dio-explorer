            Consulta rápida

              Em uma fraseLógica de programação é descrever a solução de um problema como uma sequência de passos pequenos, claros e sem ambiguidade, que um computador consegue seguir à risca.

              Algoritmo é uma receita sem “a gosto”

              O computador não adivinha nada. Uma receita que diz “sal a gosto” funciona para gente, mas não para ele. Um algoritmo é uma receita escrita para quem não sabe improvisar:

              • Entrada: os dados que chegam (os números que você digita, por exemplo).
              • Processamento: os passos, um de cada vez, sempre na mesma ordem.
              • Saída: o resultado que aparece no fim.

              Os dados ficam em variáveis: caixas com nome que guardam um valor. Em pseudocódigo, maior ← a se lê “maior recebe o valor de a”. A caixa guarda um valor por vez: quando recebe outro, o anterior some.

              Três blocos montam qualquer programa

              EstruturaO que fazExemplo
              Sequênciaexecuta uma linha depois da outrasoma ← 0
              Decisãoexecuta um bloco só se a condição for verdadeirase b > maior
              Repetiçãorepete um bloco enquanto a condição for verdadeiraenquanto i ≤ n

              Toda condição vira verdadeiro ou falso, sem meio-termo. É isso que decide para qual linha o programa vai em seguida.

                Repare: com a = 3, b = 8 e c = 5, a linha 6 nunca roda, porque 5 > 8 é falso. Na soma, as linhas 5 e 6 rodam uma vez por volta, até i ≤ n ficar falso.

                Teste de mesa: o hábito que acha bugs

                O que o simulador fez tem nome: teste de mesa. Você executa o algoritmo à mão, com papel, anotando o valor de cada variável a cada linha. Quando o resultado sai errado, a tabela mostra exatamente em que passo a coisa desandou.

                E a lógica não muda de uma linguagem para outra. O mesmo “maior de três” em JavaScript:

                let maior = a;
if (b > maior) maior = b;
if (c > maior) maior = c;
console.log(maior);

                Muda o vocabulário (if em vez de se, = em vez de ←), mas os passos são os mesmos. Quem aprende a pensar em passos aprende qualquer linguagem mais rápido.

                Teste rápido

                Depois de x ← 5 e, em seguida, x ← x + 2, quanto vale x?

                A segunda linha lê o valor atual de x (5), soma 2 e guarda o resultado de volta em x.

                No “maior de três”, com a = 9, b = 4 e c = 7, quantas vezes a variável maior recebe um valor?

                maior começa com 9, e as duas condições (4 > 9 e 7 > 9) são falsas, então as linhas de dentro dos “se” são puladas.

                O que é um teste de mesa?

                É seguir as linhas como o computador faria, com papel e caneta, para conferir se cada passo dá o resultado esperado.

                Próximo: HTML: a estrutura de toda página

                Em uma fraseHTML é a linguagem de marcação que diz ao navegador o que cada pedaço da página é: título, parágrafo, lista, link, botão. A aparência fica com o CSS, e o comportamento, com o JavaScript.

                Anatomia de uma tag

                <a href="https://www.dio.me">Visite a DIO</a>
                • Abertura <a>: o nome da tag diz o que o elemento é (a vem de anchor, um link).
                • Atributo href="...": uma configuração extra, sempre no formato nome="valor". Aqui, para onde o link leva.
                • Conteúdo: o texto que aparece na tela.
                • Fechamento </a>: o mesmo nome, com uma barra.

                Tags ficam umas dentro das outras, como caixas, e fecham na ordem inversa: <p><strong>…</strong></p>. Algumas não têm conteúdo e por isso não fecham, como <img>, <br> e <input>.

                O esqueleto de toda página

                <!DOCTYPE html>
<html lang="pt-BR">
<head>
  <meta charset="utf-8">
  <title>Minha página</title>
</head>
<body>
  <h1>Olá!</h1>
</body>
</html>
                • <head> guarda informações sobre a página: o título da aba, a codificação dos acentos. Nada dali aparece no corpo da página.
                • <body> guarda tudo o que aparece na tela.
                • lang="pt-BR" avisa o idioma, e leitores de tela pronunciam o texto do jeito certo.

                Próximo: CSS: o box model na prática

                Em uma fraseCSS decide a aparência da página, e quase tudo nela é uma caixa com quatro camadas: conteúdo, padding, borda e margem.

                As quatro camadas

                • Conteúdo (width e height): onde ficam o texto e as imagens.
                • Padding: o respiro de dentro, entre o conteúdo e a borda. Pega a cor de fundo da caixa.
                • Border: a moldura.
                • Margin: o espaço de fora. É transparente e empurra os vizinhos.

                Próximo: JavaScript: map, filter e reduce sem medo

                Em uma frasemap transforma cada item, filter escolhe alguns itens e reduce junta todos em um valor só. E nenhum dos três altera a lista original.

                Do for para uma linha

                Trabalhar com listas (os arrays) é o dia a dia de quem programa: produtos, pedidos, notas. O jeito clássico de dobrar cada número é um for:

                const numeros = [3, 8, 12, 5];

const dobro = [];
for (let i = 0; i < numeros.length; i++) {
  dobro.push(numeros[i] * 2);
}

                Com map, a mesma ideia cabe em uma linha:

                const dobro = numeros.map(n => n * 2); // [6, 16, 24, 10]

                n => n * 2 é uma arrow function: recebe um item (n) e devolve n * 2. O map chama essa função uma vez para cada item e monta um array novo com as respostas. Você diz o que fazer com cada item, e o método cuida do laço.

                Os três, lado a lado

                MétodoDevolveUse para
                mapum array do mesmo tamanho, com cada item transformadoconverter preços, formatar nomes, pegar um campo
                filterum array só com os itens em que a função devolveu truesó os ativos, só os pares, uma busca
                reduceum valor só, construído item a item num acumuladorsomar, contar, achar o maior

                Mexa e veja

                Edite a lista (separe por vírgula; decimais usam ponto) e escolha uma operação. A tabela mostra o que a função faz com cada item. Nos pares, % é o resto da divisão: 8 % 2 dá 0, então 8 é par.

                Laboratório de arrays
                map
                filter
                reduce

                Repare no reduce: na soma, o 0 no fim é o valor inicial do acumulador. No “maior” não há valor inicial, então o primeiro item vira o acumulador. E, se a lista estiver vazia, o JavaScript lança um erro: apague os números e clique em maior para ver.

                Encadeando: onde eles brilham

                Como map e filter devolvem arrays, dá para ligar um no outro. O total dos pedidos pagos:

                const pedidos = [
  { valor: 50, pago: true },
  { valor: 30, pago: false },
  { valor: 20, pago: true }
];

const total = pedidos
  .filter(p => p.pago)
  .map(p => p.valor)
  .reduce((soma, v) => soma + v, 0); // 70

                Leia de cima para baixo: fica com os pagos, pega o valor, soma. Um cuidado comum: com chaves, a arrow function precisa de return. n => { n * 2 } devolve undefined; o certo é n => { return n * 2; } ou, sem chaves, n => n * 2.

                Teste rápido

                O que [1, 2, 3].map(n => n * 10) devolve?

                map aplica a função a cada item e devolve um array novo do mesmo tamanho; quem junta tudo em um número é o reduce.

                Qual método usar para ficar só com os produtos que têm estoque?

                filter mantém os itens em que a função devolve true, como em produtos.filter(p => p.estoque > 0).

                Depois de const b = a.filter(n => n > 5), o que acontece com a?

                map, filter e reduce não alteram o array original: o resultado vai para a variável nova, b.

                Próximo: APIs e HTTP: como sistemas conversam

                Em uma fraseUma API é a porta que um sistema abre para outros programas. Na web, a conversa usa HTTP: você manda um pedido com método e rota, e recebe de volta um código de status e, quase sempre, um JSON.

                O pedido e a resposta

                Toda conversa HTTP tem duas mensagens. Quem pede (um app, um site, outro servidor) é o cliente, e a mensagem dele é a requisição:

                • Método: o verbo, ou seja, o que você quer fazer (GET, POST…).
                • Rota: em qual recurso, como /alunos ou /alunos/1.
                • Cabeçalhos: informações extras, como Content-Type: application/json (“o corpo está em JSON”).
                • Corpo: os dados que você envia, quando há dados para enviar.

                O servidor devolve a resposta: um código de status, cabeçalhos e, quase sempre, um corpo. Escrito por extenso, fica assim:

                POST /alunos HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"nome": "Carla", "trilha": "Dados"}
                HTTP/1.1 201 Created
Content-Type: application/json
Location: /alunos/3

{"id": 3, "nome": "Carla", "trilha": "Dados"}

                Quatro métodos para o CRUD

                RequisiçãoO que faz
                GET /alunos/1lê o aluno 1
                POST /alunos + corpocria um aluno
                PUT /alunos/1 + corposubstitui o aluno 1
                DELETE /alunos/1apaga o aluno 1

                Repare no padrão: /alunos é a coleção inteira e /alunos/1 é um aluno só. A mesma rota faz coisas diferentes conforme o método. E o PUT troca o recurso inteiro: campo que você não mandar some.

                Mexa e veja

                Esta API de alunos roda aqui mesmo, na memória da página. O que você cria ou apaga continua lá entre uma requisição e outra.

                Roteiro: GET /alunos, depois POST /alunos, GET /alunos/3, DELETE /alunos/1 e GET /alunos/1 de novo. Depois apague uma aspa do JSON e envie.

                Status: a resposta em três dígitos

                O primeiro dígito já conta a história: 2xx deu certo, 3xx manda você para outro endereço, 4xx é erro de quem pediu (dá para corrigir o pedido) e 5xx é erro do servidor, como o 500 Internal Server Error.

                Qual método você usa para cadastrar um aluno novo?

                POST leva os dados no corpo e o servidor cria o recurso, normalmente respondendo 201 Created.

                A API respondeu 404. O que isso diz?

                404 é “não encontrado”, um erro 4xx de quem pediu. Servidor com problema responde 5xx, e sucesso sem corpo é 204.

                Próximo: SQL: perguntas para o banco de dados

                Em uma fraseSQL é a língua para fazer perguntas a um banco de dados: você diz quais colunas quer, de qual tabela e com qual filtro, e a resposta volta como uma tabela.

                A forma de toda consulta

                SELECT nome, nota    -- quais colunas
FROM alunos          -- de qual tabela
WHERE nota > 7       -- quais linhas
ORDER BY nota DESC   -- em que ordem
LIMIT 3;             -- quantas, no máximo
                • Só SELECT e FROM são obrigatórios. O resto é opcional, mas sempre nessa ordem.
                • * no lugar das colunas quer dizer “todas”.
                • O banco não executa na ordem em que você escreve: primeiro pega a tabela (FROM), filtra as linhas (WHERE), escolhe as colunas (SELECT), ordena (ORDER BY) e só no fim corta (LIMIT). É por isso que ORDER BY + LIMIT dá “os 3 melhores”.

                Mexa e veja

                Pegadinhas de iniciante

                • Texto vai entre aspas simples: WHERE trilha = 'Python'. Sem aspas, o banco acha que Python é o nome de uma coluna.
                • Comparar usa um = só. “Diferente” é <> (a maioria dos bancos também aceita !=).
                • Sem ORDER BY, a ordem do resultado não é garantida. Se a ordem importa, peça.
                • LIMIT vale no PostgreSQL, MySQL e SQLite. No SQL Server, o jeito é SELECT TOP 3 ....
                Teste rápido

                Qual parte da consulta escolhe quais linhas entram no resultado?

                WHERE filtra as linhas; SELECT escolhe as colunas e ORDER BY só muda a ordem.

                O que SELECT nome FROM alunos ORDER BY nota DESC LIMIT 1 devolve?

                DESC ordena do maior para o menor e LIMIT 1 fica com a primeira linha. Ordenar por uma coluna que não aparece no resultado é permitido.

                Qual filtro está certo para texto?

                Em SQL, texto vai entre aspas simples e a comparação usa um = só.

                Próximo: Python: listas em 5 minutos

                Em uma fraseUma lista guarda vários valores, em ordem, dentro de uma variável só, e o Python já traz funções prontas para contar, ordenar, somar e fatiar.

                Criar e acessar

                notas = [7, 9, 5, 10, 8]
notas[0]          # 7: o índice começa em 0
notas[-1]         # 8: negativo conta do fim
notas.append(6)   # põe o 6 no final
notas[0] = 8      # troca o primeiro valor

                Pedir um índice que não existe, como notas[10], dá IndexError.

                Funções que você vai usar todo dia

                Com notas = [7, 9, 5]:

                CódigoDevolve
                len(notas)3: quantos itens
                sum(notas)21: a soma
                max(notas) e min(notas)9 e 5
                sorted(notas)[5, 7, 9]: uma lista nova, em ordem
                sorted(notas, reverse=True)[9, 7, 5]: do maior para o menor

                A média sai de graça: sum(notas) / len(notas). E atenção: sorted() não mexe na lista original. Quem ordena a própria lista é o método notas.sort(), que devolve None. Por isso notas = notas.sort() deixa você com None na mão.

                Fatiamento: [início:fim]

                Com dois pontos você pega um pedaço da lista. O início entra; o fim não entra.

                notas = [7, 9, 5, 10, 8]
notas[1:3]    # [9, 5]       índices 1 e 2
notas[:2]     # [7, 9]       do começo até antes do 2
notas[2:]     # [5, 10, 8]   do 2 até o fim
notas[-2:]    # [10, 8]      os dois últimos

                Truque para lembrar: notas[a:b] tem b − a itens. E fatia fora do limite não dá erro: notas[3:99] devolve só o que existe, [10, 8].

                Próximo: Cloud computing: IaaS, PaaS e SaaS sem confusão

                Em uma fraseCloud computing é alugar computação pela internet (servidores, bancos de dados, software pronto) e pagar pelo uso, em vez de comprar e manter tudo dentro de casa.

                Por que todo mundo foi para a nuvem

                • Sob demanda: um servidor novo sobe em minutos, sem pedido de compra nem espera pelo hardware.
                • Paga pelo uso: cobra por hora, por GB guardado ou por requisição. Desligou, parou de pagar. Esqueceu ligado, a fatura chega.
                • Elástica: na Black Friday você sobe dez máquinas; na segunda-feira, volta para duas.
                • Sem data center para cuidar: energia, refrigeração e disco queimado viram problema do provedor.

                Mexa e veja

                Todo sistema roda sobre uma pilha. Embaixo ficam rede, armazenamento e servidores (o hardware). No meio, a virtualização e o sistema operacional. Em cima, o middleware (servidor web, filas), o runtime (Node, Java, Python), os dados e a aplicação. Cada modelo de nuvem responde a uma pergunta: até que camada o provedor cuida por você?

                Os três modelos lado a lado

                ModeloVocê recebeExemplos

                infraestrutura                		máquinas virtuais, discos e rede. Do sistema operacional para cima, é com você.AWS EC2, Azure Virtual Machines, Google Compute Engine
                PaaS

                Se ajudar: on-premises é a casa própria (quebrou, você conserta). IaaS é alugar um apartamento vazio: o prédio é do dono, mas móveis e manutenção de dentro são seus. PaaS é um flat mobiliado: você só traz a mala. SaaS é o hotel: você só usa o quarto.

                Responsabilidade compartilhada

                Nenhum modelo tira tudo das suas costas. A AWS resume assim: o provedor cuida da segurança da nuvem; o cliente, da segurança na nuvem. Em qualquer modelo, continuam sendo seus:

                • Acessos: quem tem conta, senhas, MFA e permissões.
                • Dados: o que sobe, com quem é compartilhado e por quanto tempo fica guardado. Sim, até no SaaS.
                • Configuração: um bucket deixado público por engano é erro do cliente, não do provedor.
                Teste rápido

                Você criou uma máquina virtual no AWS EC2 (IaaS) e instalou o banco de dados nela. Quem aplica as atualizações de segurança do sistema operacional?

                No IaaS o provedor entrega a máquina; do sistema operacional para cima, a manutenção é sua.

                Seu time quer só fazer o deploy do código e ver o app no ar, sem cuidar de servidor nem de sistema operacional. Qual modelo combina?

                No PaaS a plataforma cuida do runtime para baixo; você entrega o código e os dados.

                A empresa usa o Microsoft 365 (SaaS) e um funcionário compartilha uma planilha sigilosa com qualquer pessoa que tenha o link. De quem é a responsabilidade?

                No SaaS o provedor cuida da plataforma, mas dados e acessos continuam com o cliente: é a responsabilidade compartilhada.

                Próximo: Testes de software: pegue o bug antes do usuário

                Em uma fraseUm teste automatizado é um pedaço de código que chama o seu código com uma entrada conhecida e confere se a saída é a esperada; se não for, ele avisa você antes que o usuário descubra.

                Anatomia de um teste

                Quase todo teste tem três passos, o famoso AAA: prepara os dados (Arrange), executa o código (Act) e confere o resultado (Assert). Em JavaScript, com o Jest, fica assim:

                // precoFinal.test.js
test('DEZ em R$ 100 dá 10%', () => {
  // 1. prepara
  const preco = 100;
  // 2. executa
  const total = precoFinal(preco, 'DEZ');
  // 3. confere
  expect(total).toBe(90);
});

                Cada caso de teste é um exemplo: uma entrada e o resultado esperado. A linha do expect é a asserção: se ela falhar, o teste fica vermelho e mostra o que esperava e o que recebeu.

                Experimente

                A função abaixo tem um bug. Rode os testes, descubra qual caso falha e aplique a correção.

                Rode os testes
                Regra de negócio: o cupom DEZ dá 10% de desconto em compras a partir de R$ 100.
                • abaixo de R$ 100: sem descontoprecoFinal(50, 'DEZ') espera 50 não rodou
                • exatamente R$ 100: ganha 10%precoFinal(100, 'DEZ') espera 90 não rodou
                • acima de R$ 100: ganha 10%precoFinal(200, 'DEZ') espera 180 não rodou
                • sem cupom: preço cheioprecoFinal(200, '') espera 200 não rodou
                • cupom que não existe: preço cheioprecoFinal(200, 'VINTE') espera 200 não rodou

                Por que o R$ 100 pegou o bug

                Os casos de R$ 50 e R$ 200 passam com ou sem o bug. Só o valor exatamente no limite mostra que > deveria ser >=. Bugs adoram fronteiras, então sempre que houver uma regra com limite, teste três pontos:

                • logo abaixo do limite (R$ 99,99);
                • exatamente no limite (R$ 100);
                • logo acima (R$ 100,01).

                E depois da correção, o teste fica na suíte para sempre: se alguém trocar o >= de volta, ele acusa a regressão (algo que funcionava e quebrou) na hora.

                Unitário, integração e ponta a ponta

                TipoO que testaTempo
                Unitáriouma função ou classe isolada, como a precoFinalmilissegundos
                Integraçãopartes conversando: código e banco de dados, serviço e APIsegundos
                Ponta a ponta (E2E)o sistema inteiro, do jeito que o usuário usa (Playwright, Cypress)minutos

                A pirâmide de testes resume a receita: muitos unitários na base (baratos e rápidos), alguns de integração no meio e poucos E2E no topo (lentos, mas pegam o que só aparece com tudo junto).

                Teste rápido

                A regra diz "frete grátis a partir de R$ 150". Qual valor é o mais importante de testar?

                Bugs adoram fronteiras: um > no lugar de >= só aparece exatamente no limite.

                Qual tipo de teste verifica uma única função isolada e roda em milissegundos?

                O teste unitário isola uma peça pequena, por isso é rápido e fica na base da pirâmide.

                Você corrigiu um bug e rodou a suíte inteira de novo, não só o teste que falhava. Para quê?

                Rodar tudo de novo pega regressões: algo que funcionava antes e quebrou com a mudança.

                Em uma fraseScrum é um framework para criar produtos em ciclos curtos, as sprints: a cada ciclo o time planeja, entrega algo que funciona, olha o resultado e ajusta o rumo.

                Quem é quem

                O Scrum Team é pequeno (em geral, 10 pessoas ou menos) e tem três responsabilidades:

                  Próximo: O que é um LLM e como ele funciona

                  Git é um sistema que guarda o histórico do seu código. Com ele você salva versões, volta no tempo quando algo quebra e trabalha em equipe sem um sobrescrever o trabalho do outro. Este guia cobre o essencial, na ordem em que você vai precisar.

                  1. Instalar

                  Windows

                  Baixe o instalador em git-scm.com/downloads e avance com as opções padrão. Ou, pelo terminal:

                  winget install --id Git.Git -e

                  macOS

                  brew install git

                  Linux (Debian e Ubuntu)

                  sudo apt update
sudo apt install git

                  Confira se deu certo:

                  git --version

                  2. Configurar (uma vez só)

                  O Git assina cada versão com seu nome e e-mail. Use o mesmo e-mail da sua conta do GitHub.

                  git config --global user.name "Seu Nome"
git config --global user.email "voce@exemplo.com"
git config --global init.defaultBranch main

                  Para ver o que ficou configurado:

                  git config --list

                  3. Começar um projeto

                  Para transformar uma pasta em um repositório:

                  cd meu-projeto
git init

                  Para baixar um repositório que já existe:

                  git clone https://github.com/usuario/repositorio.git

                  4. O ciclo do dia a dia

                  Quase tudo no Git é este ciclo: ver o que mudou, escolher o que entra e salvar uma versão.

                  git status                 # o que mudou?
git add arquivo.txt        # escolhe um arquivo
git add .                  # ou escolhe tudo
git commit -m "Explica o que foi feito"

                  Um commit é uma versão salva. Escreva mensagens curtas que digam o que mudou, como "Corrige cálculo do frete".

                  git log --oneline          # histórico resumido
git diff                   # mudanças ainda não escolhidas

                  5. Branches

                  Uma branch é uma linha paralela de trabalho. Você mexe nela sem afetar a main e junta quando terminar.

                  git switch -c minha-feature   # cria e entra na branch
git switch main               # volta para a main
git merge minha-feature       # junta a branch na main
git branch -d minha-feature   # apaga a branch já usada

                  6. Trabalhar com o GitHub

                  git remote add origin https://github.com/usuario/repositorio.git
git push -u origin main    # envia pela primeira vez
git push                   # envia os próximos commits
git pull                   # traz o que há de novo

                  7. Ignorar arquivos

                  Crie um arquivo .gitignore na raiz do projeto com o que não deve ir para o repositório:

                  node_modules/
.env
*.log

                  8. Desfazer

                  git restore arquivo.txt            # descarta mudanças não salvas no arquivo
git restore --staged arquivo.txt   # tira o arquivo do próximo commit
git commit --amend                 # corrige o último commit
git revert <id-do-commit>          # cria um commit que desfaz outro
git stash                          # guarda as mudanças para depois
git stash pop                      # traz de volta
                  Prefira git revert a apagar histórico. Ele desfaz sem reescrever o que outras pessoas já baixaram.

                  Próximo: A linha do tempo da inteligência artificial

                  A inteligência artificial parece ter surgido de repente, mas é uma história de mais de sete décadas, com períodos de euforia e de frustração. Estes são os marcos que valem a pena conhecer.

                  As ideias (1950 a 1969)

                  • 1950Alan Turing publica o artigo que pergunta se máquinas podem pensar e propõe um teste: se você conversa com uma máquina e não percebe que é uma máquina, ela passou.
                  • 1956Um encontro de pesquisadores em Dartmouth, nos Estados Unidos, dá nome à área: inteligência artificial.
                  • 1958Frank Rosenblatt apresenta o Perceptron, um neurônio artificial simples que aprende com exemplos. É o avô das redes neurais.
                  • 1966ELIZA, um dos primeiros chatbots, simula um terapeuta repetindo as frases do usuário em forma de pergunta.

                  Os invernos (1970 a 1990)

                  As promessas eram maiores que os computadores da época. O dinheiro para pesquisa secou duas vezes, nos períodos que ficaram conhecidos como invernos da IA. No meio deles, em 1986, popularizou-se o método que permite treinar redes neurais com várias camadas, a retropropagação. A ideia estava certa, mas faltavam dados e poder de processamento.

                  As máquinas começam a vencer (1997 a 2016)

                  • 1997O Deep Blue, da IBM, vence o campeão mundial de xadrez Garry Kasparov.
                  • 2012A rede neural AlexNet vence com folga uma competição de reconhecimento de imagens usando placas de vídeo. Começa a era do aprendizado profundo.
                  • 2016O AlphaGo, da DeepMind, derrota Lee Sedol no Go, um jogo considerado difícil demais para computadores.

                  A era dos modelos de linguagem (2017 em diante)

                  • 2017Pesquisadores do Google publicam "Attention Is All You Need" e apresentam o Transformer, a arquitetura por trás dos modelos atuais.
                  • 2018Surgem BERT e GPT, que mostram o poder de pré-treinar um modelo em muito texto e depois adaptá-lo a tarefas.
                  • 2020O GPT-3 escreve textos longos e coerentes a partir de uma instrução simples.
                  • 2022Geradores de imagem como Stable Diffusion e DALL·E 2 se popularizam. Em novembro, o ChatGPT leva a IA generativa ao grande público.
                  • 2023 em dianteOs modelos passam a entender imagem, áudio e código, e ganham ferramentas: navegam, executam programas e trabalham como agentes em tarefas de vários passos.

                  O que tirar disso

                  Três coisas se repetem nessa história: as ideias costumam surgir décadas antes de funcionarem, os saltos acontecem quando dados e processamento alcançam a teoria, e toda onda de euforia é seguida por ajustes de expectativa. Quem entende o básico atravessa melhor as duas fases.

                  Próximo: O que é um LLM

                  LLM é a sigla em inglês para modelo de linguagem de grande porte. É o tipo de inteligência artificial por trás do ChatGPT, do Claude e do Gemini. A definição mais útil cabe em uma linha:

                  Um LLM é um programa treinado para prever qual é o próximo pedaço de texto.

                  Todo o resto, de escrever código a resumir um contrato, sai dessa habilidade repetida milhares de vezes.

                  Tokens: as peças do texto

                  O modelo não lê letras nem palavras inteiras. Ele quebra o texto em tokens, que são pedaços de palavras. "Programação" pode virar "Program" e "ação". É em tokens que se medem o tamanho de uma conversa, o limite do modelo e o custo de uso.

                  Treinamento: aprender lendo

                  No treinamento, o modelo recebe uma quantidade enorme de texto com o final escondido e tenta adivinhar o que vem depois. A cada erro, seus bilhões de ajustes internos, os parâmetros, são corrigidos um pouco. Depois de muitas repetições ele aprende gramática, fatos, estilos e até formas de raciocinar, porque tudo isso ajuda a acertar a próxima palavra.

                  Contexto: a memória de trabalho

                  O modelo só enxerga o que está na janela de contexto: suas instruções, a conversa até ali e os arquivos que você enviou. Ele não se lembra de conversas anteriores a menos que o aplicativo coloque esse histórico de volta no contexto. Se algo importante não está lá, para o modelo não existe.

                  Temperatura: quanta variação

                  Ao escolher o próximo token, o modelo tem várias opções prováveis. A temperatura controla o quanto ele arrisca: baixa, ele escolhe quase sempre a opção mais provável e fica previsível; alta, ele varia mais e fica criativo, com mais chance de errar.

                  Alucinação: quando soa certo e está errado

                  Como o objetivo é produzir texto plausível, o modelo pode inventar um dado, uma citação ou uma função que não existe, com toda a segurança. Três hábitos reduzem o problema:

                  • Dê a fonte: cole o documento ou o código e peça a resposta com base nele.
                  • Peça que ele diga quando não souber.
                  • Confira o que importa: números, nomes, links e comandos antes de executar.

                  Como dar ao modelo o que ele não sabe

                  TécnicaO que fazQuando usar
                  PromptInstruções e exemplos na própria conversaSempre. É o primeiro passo
                  RAGBusca trechos nos seus documentos e os coloca no contextoPerguntas sobre dados seus ou recentes
                  Ajuste finoTreina o modelo um pouco mais com seus exemplosUm estilo ou formato muito específico
                  Ferramentas e agentesO modelo chama programas: busca, calculadora, terminalTarefas de vários passos

                  Um bom pedido tem quatro partes

                  1. Contexto: quem vai ler e para quê.
                  2. Tarefa: o que você quer, com um verbo claro.
                  3. Material: os dados ou o código em que ele deve se basear.
                  4. Formato: como a resposta deve vir, por exemplo uma lista de cinco itens.

                  Quem entende que o modelo é um previsor de texto com uma janela de contexto escreve pedidos melhores e desconfia na hora certa. É o que separa usar a ferramenta de depender dela.

                  Uma chave que foi parar em um repositório público costuma ser encontrada por robôs em poucos minutos. Não entre em pânico e siga esta ordem.

                  1. Revogue a chave (minutos 0 a 5)

                  Entre no painel do serviço dono da chave e revogue ou apague. Gere uma nova e guarde em variável de ambiente ou em um cofre de segredos, nunca no código.

                  Apagar a linha e fazer outro commit não resolve. A chave continua no histórico do Git e em quem já copiou o repositório.

                  2. Veja o que foi usado (minutos 5 a 15)

                  • Abra os registros de uso e de cobrança do serviço e procure chamadas que você não reconhece.
                  • Confira se foram criados recursos novos: máquinas, usuários, outras chaves, regras de acesso.
                  • Anote horários e o que foi acessado. Você vai precisar disso se houver dados de outras pessoas envolvidos.

                  3. Feche o que ficou aberto (minutos 15 a 25)

                  • Apague o que foi criado sem a sua autorização.
                  • Troque as outras credenciais que estavam no mesmo arquivo ou no mesmo ambiente.
                  • Defina um limite de gastos e alertas de cobrança no serviço.

                  4. Limpe e previna (minutos 25 a 30)

                  # tira o arquivo do controle de versão sem apagar do seu computador
git rm --cached .env
echo ".env" >> .gitignore
git commit -m "Remove arquivo de segredos do repositório"

                  Para tirar do histórico existem ferramentas próprias, como o git filter-repo. Como a chave já foi revogada, isso é limpeza, não urgência.

                  Para não repetir

                  • Mantenha um .env.example só com os nomes das variáveis, sem os valores.
                  • Ative a verificação de segredos do GitHub no repositório.
                  • Use chaves com o mínimo de permissão e uma chave diferente para cada ambiente.

                  Próximo: Como reconhecer phishing e engenharia social

                  Phishing é uma mensagem falsa que se passa por alguém de confiança para conseguir sua senha, um código ou um pagamento. Engenharia social é o nome geral para convencer uma pessoa a fazer o que o atacante quer.

                  Sete sinais para desconfiar

                  1. Urgência: "sua conta será bloqueada em 24 horas".
                  2. Remetente quase certo: um domínio parecido, com uma letra trocada ou um final diferente.
                  3. Link que não bate: o texto diz uma coisa e o endereço real é outro. Passe o mouse antes de clicar.
                  4. Pedido fora do normal: senha, código de verificação, cartão ou transferência.
                  5. Anexo inesperado: boleto, nota fiscal ou currículo que você não pediu.
                  6. Autoridade: alguém se dizendo da diretoria, do banco ou do suporte, pedindo sigilo.
                  7. Bom demais: prêmio, vaga ou reembolso que você não esperava.

                  Golpes comuns contra quem programa

                  • Falsa vaga que pede para você clonar e rodar um repositório como "teste técnico".
                  • Falso aviso de segurança do GitHub ou do npm pedindo novo login.
                  • Pacote com nome quase igual ao de uma biblioteca famosa.
                  • Mensagem de alguém do time pedindo um token "só para testar".

                  A regra que resolve quase tudo

                  Não use o link nem o telefone que vieram na mensagem. Entre no site pelo endereço que você já conhece ou fale com a pessoa por outro canal.

                  Se você clicou ou digitou a senha

                  1. Troque a senha daquele serviço agora, e de outros onde usava a mesma.
                  2. Encerre as sessões abertas e revogue tokens e chaves.
                  3. Ative o segundo fator de autenticação.
                  4. Avise o time de segurança ou quem cuida das contas. Avisar rápido reduz o estrago e não é motivo de vergonha.

                  Próximo: Senhas e segundo fator

                  A maioria das contas invadidas não foi "hackeada": a senha era reutilizada, fraca ou foi entregue em um golpe. Estes quatro hábitos fecham essas portas.

                  1. Uma senha diferente para cada serviço

                  Quando um site vaza, os atacantes testam o mesmo e-mail e a mesma senha em todos os outros. Senha única faz o vazamento parar ali.

                  2. Gerenciador de senhas

                  Ninguém decora cem senhas únicas. Um gerenciador cria e guarda senhas longas e aleatórias, e você decora só a senha principal. Faça dela uma frase longa, que é fácil de lembrar e difícil de adivinhar.

                  3. Segundo fator em tudo o que importa

                  Com o segundo fator, a senha sozinha não basta. Comece por e-mail, GitHub, nuvem e banco.

                  TipoSegurançaObservação
                  Chave de segurança ou passkeyMais altaResiste a sites falsos
                  Aplicativo autenticadorAltaGera um código que muda a cada 30 segundos
                  SMSMais baixaMelhor que nada, mas o número pode ser clonado
                  Guarde os códigos de recuperação em local seguro. Sem eles, perder o celular pode significar perder a conta.

                  4. Chaves SSH e tokens com prazo

                  • Use chave SSH com senha para o Git, em vez de digitar usuário e senha.
                  • Crie tokens com o mínimo de permissão e com data de expiração.
                  • Revogue tokens e sessões que você não usa mais.

                  Checklist de uma tarde

                  1. Instale um gerenciador de senhas.
                  2. Troque a senha do e-mail principal e ative o segundo fator nele.
                  3. Repita para GitHub, nuvem e banco.
                  4. Guarde os códigos de recuperação.
                  5. Vá trocando as senhas repetidas aos poucos, conforme usar cada serviço.
